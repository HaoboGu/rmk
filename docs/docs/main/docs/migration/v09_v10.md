# From v0.9 to v0.10

Use this guide to update an existing RMK v0.9 firmware project. For new projects, follow the current [processor guide](../features/processor).

## Processors

Update registration first, then choose whether to keep your existing run loop.

### Remove registration mode arguments

In each `keyboard.toml` keyboard module, replace `#[register_processor(event)]` or `#[register_processor(poll)]` with the bare attribute:

```diff
- #[register_processor(event)]
+ #[register_processor]
```

Registration now starts the type's `Runnable` implementation. Check the type's `#[processor]` options to preserve the behavior you want:

| Previous setup                                   | What to keep or change                                                                              |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `(poll)` with a polling processor                | Keep `poll_interval` and `poll()`.                                                                  |
| `(event)` with an event-only processor           | Keep `subscribe` without timer options.                                                             |
| `(event)` used to bypass the type's polling loop | Remove `poll_interval` to keep event-only behavior.                                                 |
| A type with a custom `Runnable`                  | Keep that implementation and its `#[runnable_generated]` marker; registration now starts your loop. |

Rust API projects that already use `run_all!` do not need a registration change.

### Use the generated deadline loop

Existing `DeadlineProcessor::deadline()` and `on_deadline()` methods keep their names. If you want RMK to generate the run loop for an existing deadline processor:

1. Add `deadline` to its `#[processor]` attribute.
2. Keep `deadline()` and `on_deadline()` in `impl DeadlineProcessor`.
3. Remove the old `impl Runnable` and `#[runnable_generated]` marker.

Keep the marker and `impl Runnable` if your custom loop is still needed. The [inactivity example](../features/processor#handle-inactivity) shows a complete processor with the generated loop.

## Battery configuration tables

Battery settings now require a dedicated table for each board. Battery fields under `[ble]`, `[split.central]`, or `[[split.peripheral]]` are no longer accepted.

Move each board's battery settings to its battery table:

| Board            | Move fields from                                                    | Move fields to                                |
| ---------------- | ------------------------------------------------------------------- | --------------------------------------------- |
| Unibody          | `[ble]`                                                             | `[battery]`                                   |
| Split central    | `[split.central]`, plus any battery settings inherited from `[ble]` | `[split.central.battery]`                     |
| Split peripheral | Its `[[split.peripheral]]` entry                                    | `[split.peripheral.battery]` below that entry |

Move `battery_adc_pin`, `adc_divider_measured`, `adc_divider_total`, `charge_state`, `charge_led`, and `battery_user_description` if configured. Leave BLE connection and pairing settings in `[ble]`.

For example, a unibody configuration changes as follows:

```diff
 [ble]
 enabled = true
+
+[battery]
 battery_adc_pin = "P0_05"
 adc_divider_measured = 2000
 adc_divider_total = 2806
```

Remove the battery fields from their old sections after moving them. Peripherals use only their own battery table and never inherit the central's battery configuration.

See [Battery configuration](../configuration/wireless#battery-configuration) for field descriptions and split keyboard examples.

## Serial numbers

Serial numbers no longer contain the RMK version, so a board keeps its serial number across upgrades. RMK builds each serial number from a protocol marker and a device serial ID. For more information, see [About serial numbers](../configuration/keyboard_device#about-serial-numbers).

How the change affects your keyboard depends on its chip:

- nRF keyboards with BLE keep their serial numbers, unless they set `serial_number`.
- Other keyboards had the RMK version in their serial numbers, so their serial numbers change once.

You don't need to remove the marker from an existing `serial_number`. RMK replaces a `vial:f64c2b3c` or `rynk:` marker already in it, so `vial:f64c2b3c:000001` and `000001` give the same serial number.

To update your project:

1. If you set `serial_number` for an nRF keyboard with BLE, remove it to keep the serial number the keyboard reports now. Earlier versions ignored this value on these keyboards.
2. If you use `rmk::config::RMK_BUILD_INFO`, remove it. If you passed it as `serial_number`, remove that field to use the default device serial ID.
3. With the Rust API, replace a literal `serial_number` with `rmk::config::build_serial_number(Some("board-0001"), &[])`, using your existing ID. The field now owns the complete serial number, including the protocol marker.
4. Replace `serial_number_from_uid(&uid)` with `build_serial_number(None, &uid)`. `rp2040_serial_number` also returns a complete, owned serial number.
5. `DeviceConfig` is now `Clone` rather than `Copy`. If USB and BLE share a configuration, pass `rmk_config.device_config.clone()` to USB before moving `rmk_config` into BLE.
