# From v0.8 to v0.9

v0.9 is a major release. It introduces [Rynk](../features/rynk) (RMK's optional native host
protocol), display support, DFU firmware update, and a hardware watchdog; it unifies the input
device / controller Rust APIs into a single processor model, restructures `keyboard.toml`, moves to
newer embassy and BLE stacks, and re-enables the storage build-hash guard.

Two things happen on the very first v0.9 boot regardless of how you use RMK:

- **On-keyboard storage is reset** — saved keymap edits, macros, and BLE bonds are erased (see
  [Storage is reset](#storage-is-reset-when-v09-first-boots)).
- **BLE hosts must re-pair** — forget the keyboard on every bonded host and pair again (see
  [BLE hosts must forget and re-pair](#ble-hosts-must-forget-and-re-pair)).

Each change below is labeled with who it affects. Use the table to find what applies to you, then
follow the steps in that section. Changes are grouped as **Everyone** and **Rust API developers**
(`examples/use_rust`); `keyboard.toml` users (`examples/use_config`) are affected only by the
**Everyone** changes.

## Everyone

### Storage is reset when v0.9 first boots

**Who this affects:** every keyboard built with the (default) `storage` feature.

v0.9 re-enables the storage build-hash guard: the storage region is stamped with a hash of the
firmware build, and on boot a mismatch erases the whole region and re-initializes it from the
compiled-in defaults. v0.8.2 shipped with this guard disabled, so upgrading is the first time most
keyboards hit it.

On the first v0.9 boot you lose everything saved on the keyboard:

- keymap edits, macros, and behavior changes made from Vial (or any host tool)
- BLE bond/profile information (see the [re-pairing section](#ble-hosts-must-forget-and-re-pair))
- stored split peer addresses — halves re-pair with each other automatically on the next boot

The guard also changes day-to-day behavior going forward: the hash covers the build itself, so
**every newly flashed firmware resets the storage again**. Treat your `keyboard.toml` / Rust keymap
as the source of truth and export anything you configured from the host side before upgrading.

### BLE hosts must forget and re-pair

**Who this affects:** every BLE keyboard.

Three independent v0.9 changes each require re-pairing, so there is no way around it:

- All HID reports moved into a single HID service (fixes media/mouse keys on Android, which only
  attaches to the first HID service). Bonded hosts cache the old GATT layout.
- HID report ids were renumbered (`Keyboard=1`, `Mouse=2`, `Media=3`, `System=4`). USB hosts re-read
  report ids on every plug-in and are unaffected; bonded BLE hosts do not.
- The [storage reset](#storage-is-reset-when-v09-first-boots) erases the keyboard's side of every
  bond anyway.

After flashing v0.9: delete/forget the keyboard in the Bluetooth settings of **every** host it was
paired with, then pair again. Split halves re-bond with each other automatically.

### Hardware watchdog is new and on by default

**Who this affects:** everyone; automatic for `keyboard.toml` users.

v0.8 had no watchdog support. v0.9 adds a `watchdog` feature **and enables it by default**: the
chip's hardware watchdog is armed and fed by a dedicated task, so a hung firmware now resets instead
of staying dead until power-cycled.

- **`keyboard.toml` users:** nothing to do. The macro wires the watchdog automatically on RP2040,
  nRF52, and ESP32; on other chips the feature is a no-op. To turn it off, set
  `default-features = false` and list your features without `watchdog`.
- **Rust API users:** the feature alone does nothing — you must construct a watchdog runner and pass
  it to `run_all!`, as shown in [the `run_all!` section](#run_rmk-is-replaced-by-transports-and-run_all).
  Skip the runner (or the feature) if you don't want the watchdog.

### `keyboard.toml` layout restructured

**Who this affects:** everyone using `keyboard.toml`.

The keyboard description is now split into three sections: `[matrix]` (electrical wiring, unchanged),
`[layout]` (physical arrangement), and the new `[keymap]` (layer count and key actions). The
layer-related fields move out of `[layout]` into `[keymap]`:

| Old (v0.8)                       | New (v0.9)                  |
| -------------------------------- | --------------------------- |
| `[layout].matrix_map`            | `[layout].map`              |
| `[layout].layers`                | `[keymap].layers`           |
| `[[layer]]`                      | `[[keymap.layer]]`          |
| `[layout].keymap` (removed)      | `[[keymap.layer]]`          |
| `[layout].encoder_map` (removed) | `[[keymap.layer]].encoders` |

`[layout].rows` and `[layout].cols` stay in `[layout]`.

**Before (v0.8):**

```toml
[layout]
rows = 2
cols = 3
layers = 2
matrix_map = """
(0,0) (0,1) (0,2)
(1,0) (1,1) (1,2)
"""

[[layer]]
name = "base"
keys = """
A B C
D E F
"""
```

**After (v0.9):**

```toml
[layout]
rows = 2
cols = 3
map = """
(0,0) (0,1) (0,2)
(1,0) (1,1) (1,2)
"""

[keymap]
layers = 2

[[keymap.layer]]
name = "base"
keys = """
A B C
D E F
"""
```

**If you used the 3D-array form** (`keymap = [[["A", "B", ...]]]` with no `matrix_map`): there is no
direct rename for you — `[layout].map` is now required whenever `[[keymap.layer]]` layers exist.
Author a `map` that lists the `(row,col)` position of every key in visual order (as in the example
above), then move each layer of the old array into a `[[keymap.layer]]` `keys` string.

Unknown or leftover `keyboard.toml` keys that v0.8 silently ignored are now build errors, so stray
old-schema keys will be flagged for you.

### `[rmk]` channel keys replaced by `[event]`

**Who this affects:** `keyboard.toml` users who tuned event/controller channel sizes.

The global channel knobs under `[rmk]` were removed and are now per-event settings in the new
`[event]` section. Because unknown keys are rejected, the old keys fail the build:

| Old (v0.8) `[rmk]` key    | New (v0.9)                      |
| ------------------------- | ------------------------------- |
| `event_channel_size`      | `[event.<name>]` `channel_size` |
| `controller_channel_size` | `[event.<name>]` `channel_size` |
| `controller_channel_pubs` | `[event.<name>]` `pubs`         |
| `controller_channel_subs` | `[event.<name>]` `subs`         |

Event names and their defaults are listed in `rmk-config/src/default_config/event_default.toml`; set
only the events you need to change, e.g.:

```toml title="keyboard.toml"
[event.keyboard]
channel_size = 32
```

Also, `[rmk].mouse_key_interval` and `[rmk].mouse_wheel_interval` are now 16-bit — values above
65535 are rejected.

### Morse timeouts are capped at 8191 ms

**Who this affects:** anyone with `hold_timeout`, `gap_timeout`, or `quick_tap_timeout` above 8191 ms
(in `keyboard.toml` or Rust).

Morse/tap-hold timing now packs into 13 bits, capping each timeout at 8191 ms. In `keyboard.toml`,
values above the cap fail the build with an explicit error; the Rust `MorseProfile` setters clamp
them to the cap. Lower the value below the cap. (Internally, `MorseProfile` is now a packed `u64`
instead of a `u32` — only relevant if you manipulated the raw representation.)

### Dependency updates

**Who this affects:** everyone — these versions live in your own `Cargo.toml`.

v0.9 moves to newer embassy and BLE-stack releases. The main version bumps:

| Dependency           | v0.8 | v0.9 |
| -------------------- | ---- | ---- |
| `embassy-executor`   | 0.9  | 0.10 |
| `embassy-sync`       | 0.7  | 0.8  |
| `embassy-usb`        | 0.5  | 0.6  |
| `embassy-rp`         | 0.8  | 0.10 |
| `embassy-nrf`        | 0.8  | 0.11 |
| `esp-hal`            | 1.0  | 1.1  |
| `trouble-host` (BLE) | 0.5  | 0.7  |
| `bt-hci` (BLE)       | 0.6  | 0.9  |

`embassy-time` is unchanged (0.5).

These are not drop-in version bumps — several come with code changes:

- **embassy-executor 0.10** renames the `arch-cortex-m` feature to `platform-cortex-m` and changes
  task-spawn call sites.
- **embassy-rp 0.10**: `Flash::new` takes the interrupt struct; add
  `DMA_IRQ_0 => dma::InterruptHandler<DMA_CH0>` to your `bind_interrupts!`.
- **nRF BLE**: the `nrf-sdc` / `nrf-mpsl` git `rev` moves forward, the `support_*` builder methods
  no longer return `Result` (drop those `?`s), and memory-block sizes changed. Copy the exact `rev`
  and setup from the matching example.
- **pi_pico_w**: cyw43 now needs a fourth firmware blob (`nvram_rp2040.bin`) and updated task wiring.
- **ESP32**: examples add a `[patch.crates-io]` block pinning the esp-hal graph for bt-hci 0.9
  compatibility, plus `esp-radio` / `esp-rtos` version bumps — copy the whole block as-is.

The fastest path is to diff your `Cargo.toml` and `main.rs` against the matching example under
`examples/` for your chip and take its versions wholesale.

### Rynk is a new optional host protocol

[Rynk](../features/rynk) is RMK's native host protocol and a new opt-in alternative to Vial. Vial
remains the default host protocol. The `rmk` crate's default features changed in two ways: the
removed `vial_lock` feature is replaced by the protocol-neutral `host_lock` feature, and the new
[`watchdog`](#hardware-watchdog-is-new-and-on-by-default) feature is on by default:

| v0.8 default features                   | v0.9 default features                               |
| --------------------------------------- | --------------------------------------------------- |
| `defmt`, `storage`, `vial`, `vial_lock` | `defmt`, `storage`, `vial`, `host_lock`, `watchdog` |

Rynk and Vial are mutually exclusive — enable exactly one. If you relied on the defaults, your
firmware continues to use Vial with its physical-presence lock.

#### If you use keyboard.toml

The `[host]` section must match the `rmk` Cargo features — RMK checks this when it builds and stops
with an error if they disagree.

To keep Vial, no host-protocol changes are needed. The default `[host]` values continue to match the
`rmk` default features.

To opt into Rynk, update `[host]`:

```toml title="keyboard.toml"
[host]
vial_enabled = false
rynk_enabled = true
```

Then turn off default features and explicitly enable `rynk` along with the other features you need:

```toml title="Cargo.toml"
rmk = { version = "0.9", default-features = false, features = [
    "defmt",
    "storage",
    "rynk",
    "watchdog",
    # ...your chip and other features
] }
```

See [Host Configuration](../configuration/host_config) for the full set of options.

#### If you use the Rust API

Rust projects that list `vial` explicitly do not need to change it. To move to Rynk, disable default
features and replace `vial` (and `vial_lock`) with `rynk` in your explicit feature list.

Wiring is protocol-agnostic: `HostService` resolves to whichever of `rynk` or `vial` you enabled, so
the setup shown in [the `run_all!` section](#run_rmk-is-replaced-by-transports-and-run_all) is the
same for both.

### Experimental protocol features renamed

**Who this affects:** the rare early adopters who enabled the experimental protocol features from a
post-0.8.2 git snapshot of RMK (they never shipped in a 0.8.x release).

If your `Cargo.toml` used the experimental feature `rmk_protocol`, rename it to `rynk`. The separate
`bulk_transfer` feature is gone — bulk transfers are now always on with `rynk` and sized by the
`[rmk].rynk_buffer_size` knob, so just drop `bulk_transfer` from your feature list.

| Old             | New (v0.9)                                  |
| --------------- | ------------------------------------------- |
| `rmk_protocol`  | `rynk`                                      |
| `bulk_transfer` | removed — always on, use `rynk_buffer_size` |

The `[rmk].protocol_max_bulk_size` key was likewise removed; `[rmk].rynk_buffer_size` is now the
single knob for bulk-transfer throughput.

## Rust API developers

Every example's `main()` was rewritten between v0.8 and v0.9. The fastest migration is to open the
v0.9 example for your chip under `examples/use_rust/`, take its `main.rs` structure, and port your
customizations into it. The sections below explain each change so you can map your own code.

### `run_rmk` is replaced by transports and `run_all!`

**Who this affects:** every Rust API user.

`run_rmk` (and the `join`/`run_devices!` pattern around it) is gone. In v0.9 each piece of the
firmware — matrix, storage, transports, host service, processors, keyboard, watchdog — is a runnable
passed to a single `run_all!` call, and the USB/BLE plumbing that `run_rmk` hid is now an explicit
transport you construct.

Before (v0.8):

```rust
use rmk::channel::EVENT_CHANNEL;
use rmk::futures::future::join3;
use rmk::{initialize_keymap_and_storage, run_devices, run_rmk};

let (keymap, mut storage) =
    initialize_keymap_and_storage(&mut default_keymap, flash, &storage_config, &mut behavior_config, &mut per_key_config).await;

let mut matrix = Matrix::<_, _, _, ROW, COL, true>::new(row_pins, col_pins, debouncer);
let mut keyboard = Keyboard::new(&keymap);

join3(
    run_devices! (
        (matrix) => EVENT_CHANNEL,
    ),
    keyboard.run(),
    run_rmk(&keymap, driver, &mut storage, rmk_config),
)
.await;
```

After (v0.9):

```rust
use rmk::host::HostService;
use rmk::usb::UsbTransport;
use rmk::watchdog::Rp2040Watchdog;
use rmk::{KeymapData, initialize_keymap_and_storage, run_all};

let (keymap, mut storage) =
    initialize_keymap_and_storage(&mut keymap_data, flash, &storage_config, &mut behavior_config, &per_key_config).await;

let mut matrix = Matrix::<_, _, _, ROW, COL, true>::new(row_pins, col_pins, debouncer);
let mut keyboard = Keyboard::new(&keymap);

// The host service (Vial or Rynk) attaches to each transport that should serve it.
let host_service = HostService::new(&keymap, &rmk_config);
let mut usb_transport = UsbTransport::new(driver, rmk_config.device_config).with_host_service(&host_service);

// New in v0.9: the hardware watchdog runner (RP2040 shown; see your chip's example for the
// Nrf52Watchdog / Esp32Watchdog setup).
let mut watchdog_runner = Rp2040Watchdog::default_runner(embassy_rp::watchdog::Watchdog::new(p.WATCHDOG));

run_all!(matrix, storage, usb_transport, keyboard, watchdog_runner).await;
```

Key points:

- `run_rmk`, `run_devices!`, `run_processor_chain!`, and `rmk::channel::EVENT_CHANNEL` no longer
  exist. `storage` and `keyboard` are ordinary runnables inside `run_all!` — no more
  `keyboard.run()` in a `join`.
- On BLE boards, build the BLE transport from the stack (`BleTransport::new` is async, and it takes
  `rmk_config` **by value**, so construct `UsbTransport` — which only needs
  `rmk_config.device_config` — first):

  ```rust
  let mut ble_transport = BleTransport::new(&stack, rmk_config)
      .await
      .with_host_service(&host_service);

  run_all!(matrix, storage, usb_transport, ble_transport, keyboard, watchdog_runner).await;
  ```

- On split peripherals, `run_rmk_split_peripheral` lost its storage argument — it now takes just
  `(id, &stack)` (BLE) or the serial port, and the peripheral's storage is passed to `run_all!` as
  its own runnable.
- Optional processors (WPM, battery, LED indicator, display, ...) are constructed and added to the
  same `run_all!` list.

### Keymap and storage initialization

**Who this affects:** every Rust API user.

`initialize_keymap_and_storage` now takes a `KeymapData` wrapper instead of a `&mut` keymap array,
and the positional config is passed by shared reference. `initialize_encoder_keymap_and_storage` is
removed — encoders go through `KeymapData` too:

```rust
// Before (v0.8)
let mut default_keymap = keymap::get_default_keymap();
let (keymap, mut storage) = initialize_keymap_and_storage(
    &mut default_keymap, flash, &storage_config, &mut behavior_config, &mut per_key_config,
).await;

// After (v0.9)
let mut keymap_data = KeymapData::new(keymap::get_default_keymap());
// With rotary encoders (replaces initialize_encoder_keymap_and_storage):
// let mut keymap_data = KeymapData::new_with_encoder(keymap::get_default_keymap(), keymap::get_default_encoder_map());
let (keymap, mut storage) = initialize_keymap_and_storage(
    &mut keymap_data, flash, &storage_config, &mut behavior_config, &per_key_config,
).await;
```

### One processor model for devices and controllers

**Who this affects:** anyone who wrote a custom input device, input processor, controller, or custom
event.

v0.8 had two parallel systems: the `InputProcessor` trait with `run_processor_chain!` on the input
side, and the `Controller` / `EventController` / `PollingController` traits (with `.event_loop()`)
on the output side, connected by the central `rmk::event::Event` enum (`Event::Custom` for your own
data). v0.9 replaces all of that with one processor model built on typed events:

- **Events** are your own structs annotated with `#[event(...)]` (or enums with `#[derive(Event)]`),
  each with its own pub/sub channel. The central `Event` enum and `Event::Custom` are gone.
- **Input devices** implement `InputDevice` (`type Event` + `async fn read_event`) and are annotated
  with `#[input_device(publish = YourEvent)]`, which generates the run loop that publishes events.
- **Processors** subscribe to events with `#[processor(subscribe = [YourEvent])]` and replace both
  input processors and controllers. `EventController::event_loop()` is gone — pass the processor to
  `run_all!`.
- **`Runnable` moved** from `rmk::input_device::Runnable` to `rmk::core_traits::Runnable`, and its
  signature is now `async fn run(&mut self) -> !` — implementations must loop forever instead of
  returning.
- **`PollingController` became `PollingProcessor`** (`rmk::processor::PollingProcessor`): the
  `const INTERVAL` associated constant is now an `interval()` method, and the periodic work goes in
  `async fn update`:

  ```rust
  // Before (v0.8)
  impl PollingController for MyDevice {
      const INTERVAL: Duration = Duration::from_millis(10);
      async fn update(&mut self) { /* ... */ }
  }

  // After (v0.9)
  impl PollingProcessor for MyDevice {
      fn interval(&self) -> Duration {
          Duration::from_millis(10)
      }
      async fn update(&mut self) { /* ... */ }
  }
  ```

The built-in controllers were renamed and moved accordingly:

| Old (v0.8)                                                    | New (v0.9)                                                           |
| ------------------------------------------------------------- | -------------------------------------------------------------------- |
| `rmk::controller::led_indicator::KeyboardIndicatorController` | `rmk::processor::builtin::led_indicator::KeyboardIndicatorProcessor` |
| `rmk::controller::battery_led::*`                             | `rmk::processor::builtin::battery_led::*`                            |
| WPM controller                                                | `rmk::processor::builtin::wpm::WpmProcessor`                         |

See `examples/use_rust/` (e.g. the split central and display examples) for complete custom-device
and custom-processor setups.

#### If you tracked unreleased main

If your code was written against a post-0.8.2 git snapshot that already had the macro system, only
the names changed:

| Old                                                                | New                                     |
| ------------------------------------------------------------------ | --------------------------------------- |
| `#[controller]` / `#[input_processor]`                             | `#[processor]`                          |
| `#[controller_event]` / `#[input_event]`                           | `#[event]`                              |
| `#[derive(InputEvent)]`                                            | `#[derive(Event)]`                      |
| `#[register_controller]`                                           | `#[register_processor]`                 |
| `publish_controller_event[_async]` / `publish_input_event[_async]` | `publish_event` / `publish_event_async` |

### Removed Cargo features: `controller` and `col2row`

**Who this affects:** Rust users who list either feature in `Cargo.toml`.

Both features no longer exist, and listing them is a hard cargo error
(`package 'rmk' does not have feature ...`):

- `controller` — obsolete with the [unified processor model](#one-processor-model-for-devices-and-controllers);
  `split` no longer implies it. Just delete it.
- `col2row` — matrix direction is not feature-gated anymore. The `Matrix` const-generic bool you
  already pass (`Matrix::<_, _, _, ROW, COL, true>`) keeps working unchanged; delete the feature.

### BLE and split setup changes

**Who this affects:** Rust API users with BLE and/or split keyboards.

- `build_ble_stack` lost its RNG parameter: `build_ble_stack(controller, addr, &mut resources)`.
  The `rand_core` / `rand_chacha` dependencies the old signature forced can be removed from your
  `Cargo.toml`.
- `BleTransport::new(&stack, rmk_config).await` replaces the BLE plumbing inside the old `run_rmk`
  (see [the `run_all!` section](#run_rmk-is-replaced-by-transports-and-run_all)).
- `NrfAdc::new` gained a required `event_device_ids` array argument (one id per ADC event source):

  ```rust
  let mut adc_device = NrfAdc::new(
      saadc,
      [AnalogEventType::Battery],
      [0], // new: event device ids
      embassy_time::Duration::from_secs(12),
      None,
  );
  ```

- `BatteryProcessor::new(low_mv, high_mv)` no longer takes a `&keymap` argument.
- `OffsetMatrixWrapper` is removed — split centrals use the plain `Matrix` type now.
- The free function `read_peripheral_addresses` became a storage method:
  `storage.read_peripheral_addresses::<N>()`.

### Pointing device API renamed

**Who this affects:** anyone constructing a pointing device in Rust.

The generic `PointingDevice` / `PointingProcessor` replace the PMW3610-specific `Pmw3610Device` /
`Pmw3610Processor`. `PointingDevice` names the sensor as a type parameter and takes a new leading
device-id argument (the id you reference from auto-mouse-layer config); `PointingProcessor::new`
gains a `PointingProcessorConfig`:

```rust
// Before (v0.8)
let device = Pmw3610Device::new(spi, cs, motion_pin, config);
let processor = Pmw3610Processor::new(&keymap);

// After (v0.9)
let device = PointingDevice::<Pmw3610<_, _, _>>::new(0, spi, cs, motion_pin, config); // 0 = device id
let processor = PointingProcessor::new(&keymap, PointingProcessorConfig::default());
```

keyboard.toml users don't need to do anything — the TOML config is unchanged.

### MouseKeyConfig fields renamed

**Who this affects:** anyone building a `MouseKeyConfig` in Rust. (keyboard.toml users are unaffected —
the `[rmk]` `mouse_key_interval` / `mouse_wheel_interval` settings are unchanged.)

| Old (v0.8)                   | New (v0.9)           |
| ---------------------------- | -------------------- |
| `time_to_max`                | `ticks_to_max`       |
| `wheel_time_to_max`          | `wheel_ticks_to_max` |
| `wheel_max_speed_multiplier` | `wheel_max_speed`    |

The renames reflect that these values count acceleration **ticks**, not milliseconds.

### Tap-hold macros take a profile index

**Who this affects:** Rust keymaps that set custom tap-hold timing profiles, or that construct
`KeyAction::TapHold` directly. (keyboard.toml users are unaffected — the macro interns profiles by
name automatically.)

`KeyAction::TapHold` now carries a `u8` index into the morse-profile table instead of an inline
`MorseProfile`. The custom-profile macros `thp!` / `mtp!` / `ltp!` / `ttp!` take that index as their
last argument: populate `behavior.morse.profiles` and pass the 0-based index of the profile you want.
An index with no matching entry falls back to the default profile. The default-profile macros `th!` /
`mt!` / `lt!` / `tt!` are unchanged.

Also note that timeouts inside a profile are [capped at 8191 ms](#morse-timeouts-are-capped-at-8191-ms).

## Automatic changes (usually no action)

- **Event channel subscriber counts.** Several events had their default `subs` count increased to make
  room for Rynk's host sessions. This is applied automatically. You only need to act if you **pinned
  custom `[event.<name>]` `subs` values** — recheck them against the new defaults. When enabling Rynk,
  also make sure there are enough subscriber slots, or the keyboard will panic on connect.
- **`keyboard.toml` rejects unknown keys.** A leftover or misspelled key that v0.8 silently ignored is
  now an error at build time. No action unless the build complains — then remove or fix the flagged key.

## New in v0.9 (no migration needed)

These are new capabilities, listed so you know they exist:

- **Display support** — SSD1306 / SH1106 / SH1107 / SH1108 / SSD1309 OLEDs and a wide range of TFT
  panels (ST7735/ST7789/ILI9341/GC9A01/...), configured from `keyboard.toml` `[display]` or the Rust
  API.
- **DFU firmware update** — `dfu` / `dfu_rp` / `dfu_nrf` / `dfu_split` features with the `rmk-boot`
  bootloader, gated by a physical-presence `dfu_lock`. Split DFU currently supports serial splits
  only.
- **Auto mouse layer** — activate a layer automatically while a pointing device is moving.
- **`quick_tap_timeout`** — re-press a tap-hold key quickly to get OS auto-repeat of the tap.
- **`bootmagic`** — hold a designated key during boot to drop into the chip bootloader (works per-half
  on splits).
- **`rmk::boot` is now public** — call `rmk::boot::jump_to_bootloader()` from your own code.
- **`PDF(n)`** — persistent default layer switching is now accepted in `keys` strings.
- **`ClearEeprom` keycode works** — pressing it resets the storage (requires `storage`).
- **New input-device drivers** — Azoteq IQS5xx trackpad and PMW3360 / PMW3389 mouse sensors, plus a
  `report_hz` option for the PMW3610.

See the [changelog](https://github.com/rmk-rs/rmk/blob/main/rmk/CHANGELOG.md) for the complete list.

## Why these changes?

- **Rynk** gives RMK a native host protocol that understands every RMK feature, instead of being
  limited to what the Vial standard supports.
- **The unified processor model** collapses two parallel systems into one: a single `#[event]`
  macro, a single `#[processor]` macro, and one `run_all!` — simpler to learn and maintain, with no
  loss of functionality.
- **The storage build-hash guard** prevents new firmware from misreading data an older firmware
  stored, which matters in v0.9 because the stored keymap encoding changed.
